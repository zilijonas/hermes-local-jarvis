# Troubleshooting

Repo: `/Users/agent/ai/repos/hermes-jarvis-voice`. Start with
`scripts/status.sh` (read-only) for a one-screen snapshot before anything below.

| Symptom | Check | Fix |
|---|---|---|
| jarvisd offline | `launchctl print gui/$(id -u)/local.jarvis.jarvisd \| head -20` — look for `state = running` and a `pid`. Then `curl -s 127.0.0.1:9140/health`. | If not loaded: `scripts/install.sh` (idempotent) re-bootstraps it. If loaded but crashing: `tail -50 ~/.hermes/profiles/jarvis-voice/logs/jarvisd.err.log` and `.../jarvisd.out.log` (uvicorn access/crash lines) plus `.../jarvisd.log` (app's own rotating log). Manual restart: `launchctl kickstart -k gui/$(id -u)/local.jarvis.jarvisd`. |
| dashboard 9131 down | `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9131/jarvis` — expect 200. `launchctl print gui/$(id -u)/local.jarvis.dashboard \| head -20`. | Logs: `~/.hermes/profiles/jarvis-voice/logs/dashboard.{out,err}.log`. Restart: `launchctl kickstart -k gui/$(id -u)/local.jarvis.dashboard`. If it won't start, check port 9131 isn't already bound: `lsof -i :9131`. |
| plugin tab missing from dashboard | `curl -s 127.0.0.1:9131/api/dashboard/plugins \| grep jarvis-voice`. If absent, check the symlink: `ls -la ~/.hermes/profiles/jarvis-voice/plugins/jarvis-voice` — must point to `<repo>/hermes-plugin`. | Re-link: `scripts/install.sh` (step 2 recreates it if stale/missing). Then force a rescan (needs the browser's session token — a bare `curl` gets `{"detail":"Unauthorized"}`; use the dashboard UI's own reload, or open the Network tab to copy the real request). Restarting `local.jarvis.dashboard` also picks up a new/changed `plugin_api.py` — it is imported once at server startup only. |
| Ollama down / model evicted | `ollama ps` — ground truth for what's actually resident. **Do not trust** `/health`'s `models.mediator/worker.resident` field alone: verified 2026-07-27, it compares the bare config name (e.g. `granite4.1-local-64k`) against `/api/ps` entries that carry a `:latest` tag suffix, so it reports `resident:false` even when `ollama ps` shows the model loaded. | If Ollama itself is down: check its own LaunchAgent/process, restart it, then `curl 127.0.0.1:9140/health` again (mediator/STT/TTS retry with backoff automatically). If a model was evicted: this box keeps roughly one large model resident at a time (~24 GB, ~10 GB per big model) — swapping mediator↔worker is normal and costs a cold load, not a bug. Cold-load latencies measured on this box: gemma4:e4b-it-qat ≈ 6.3 s, granite4.1-local-64k first token can push a `hermes -z` one-shot to 60–90+ s if it has to swap back in after the mediator ran. Warm round-trips are 0.2–0.4 s (granite) / 0.38 s (gemma). |
| mic permission blocked in browser | Browser padlock/site settings for `127.0.0.1:9131` → Microphone. Safari/Chrome both treat `127.0.0.1` as a secure origin so `getUserMedia` should prompt; if it silently fails, check macOS System Settings → Privacy & Security → Microphone for the browser itself. | Grant permission, reload `/jarvis`. If still silent, check the browser console for `NotAllowedError` vs `NotFoundError` (no input device) vs a `mic-worklet.js` load failure (see next row for asset path). |
| no audio out | Confirm TTS is actually healthy: `curl -s 127.0.0.1:9140/health \| grep -o '"tts":{[^}]*}'` — expect `"ok":true,"detail":"kokoro resident"`. Test end-to-end: `curl -s -X POST 127.0.0.1:9140/say -H 'Content-Type: application/json' -d '{"text":"test","interrupt":false}'`. | If kokoro isn't resident: check `~/ai/models/kokoro/kokoro-v1.0.onnx` and `voices-v1.0.bin` exist and are readable. If kokoro fails to load, jarvisd falls back to macOS `/usr/bin/say` — confirm `say` still works standalone. In-browser: check `player-worklet.js` loaded (Network tab) and the tab isn't muted/backgrounded (Safari suspends audio contexts in background tabs). |
| STT garbage / wrong transcript | Check input gain and echo: is TTS output leaking into the mic (no physical isolation, speakers instead of headphones)? jarvisd's echo rejection drops STT text matching the tail of what Jarvis just spoke — a wrong/garbled transcript that doesn't match anything Jarvis said is a genuine STT miss, not an echo-gate bug. | Use headphones or lower speaker volume to test in isolation. Check VAD `aggressiveness`/`endpoint_ms` in `service/jarvisd.toml` `[vad]` (default `aggressiveness=2`, `endpoint_ms=500`) — a too-aggressive VAD can clip word starts. Confirm `[stt] compute="int8" device="cpu"` hasn't been changed to something unsupported on this box. |
| worker tasks failing / stuck | Smoke-test the profile directly: `hermes -p jarvis-voice -z "Reply with exactly: JARVIS-OK" --yolo` — expect `JARVIS-OK`. Verify granite is actually resident: `ollama ps`. Check the task via `curl -s 127.0.0.1:9140/tasks/<id>`. | If the smoke test itself fails: read the stderr, check `~/.hermes/profiles/jarvis-voice/config.yaml` `model.*`/`auxiliary.*` blocks weren't hand-edited into inconsistency. If it's just slow: see the Ollama model-swap row above — one-shot cold path measured 79–92 s on this box, that's expected, not a hang. If tool calls themselves fail: the worker is deliberately lean (5 toolsets minus a long `disabled_toolsets` list, plus a `-t` sub-selection per spawn of 1–3 toolsets) — a task naming a tool outside its granted toolsets will fail to find it; that's a capability-routing/toolset-selection bug to fix in code, not a runtime outage. |
| memory search empty | `curl -s '127.0.0.1:9140/memory/search?q=test&k=3'`. Check `component_status` under `/health` — if the embeddings table is empty, nomic-embed-text embeddings never ran. | Reindex is incremental and in-process on jarvisd's own schedule; a full restart also triggers a fresh incremental pass: `launchctl kickstart -k gui/$(id -u)/local.jarvis.jarvisd`. Confirm Ollama has `nomic-embed-text` pulled (`ollama list`) and reachable — embeddings silently skip (not error) if Ollama is down, per `service/tests/test_memory.py`'s own `OLLAMA_UP` skip gate. |
| high RAM usage | `ollama ps` (ground truth residency + size), `curl -s 127.0.0.1:9140/health \| grep free_gb`, `vm_stat`. This box: gemma4:e4b-it-qat ≈ 6.1 GB, granite4.1-local-64k ≈ 5.3 GB disk / up to ~10 GB resident at 65536 ctx — both resident simultaneously is the worst case (~11–12 GB per ARCHITECTURE.md's RAM plan). | If memory is genuinely tight, drop `[ollama] keep_alive` in `service/jarvisd.toml` (currently `"30m"`) toward `"0"` for the worker path, or reduce `mediator_num_ctx` (currently 8192). Restart jarvisd to pick up config edits: `launchctl kickstart -k gui/$(id -u)/local.jarvis.jarvisd`. |
| false `Unauthorized` on `/api/plugins/...` or `/api/dashboard/plugins/rescan` | Confirmed live 2026-07-27: a bare `curl` against these routes returns `{"detail":"Unauthorized"}` — this is correct behavior, not a bug. The dashboard gates its API behind a per-session token (`window.__HERMES_SESSION_TOKEN__`, header `X-Hermes-Session-Token`). | From a browser (already authenticated) it works. From the CLI, either copy the token out of the browser's Network tab / `X-Hermes-Session-Token` request header, or hit jarvisd directly on `127.0.0.1:9140` (no auth, loopback-only) instead of going through the dashboard proxy on 9131. |
